## 第 17 讲｜11/17：软件工厂与自改进的软件系统

### 1. 课程事务（Logistics）
- 作业 6 周日截止；周四嘉宾 Michele Catasta（Replit 总裁），讲座在 STLC 111。

### 2. 为什么是现在
- 编程代理已经很强，软件任务的编排正在从「人在回路里」（in the loop）转向「人在回路上」（on the loop）。
- 大多数软件工作的形式相对固定，所以这是自动化工作流的下一步。

### 3. 定义：软件工厂的三个部分
- **生产线**：一组云端后台代理，从任务的来源（issue、Slack 线程、Sentry 告警、定时任务）接活，在隔离环境里完成，交回 PR。
- **质检**：CI、静态分析、测试和 AI 审查员，用同一个标准检查每一份产出，不管是谁或什么发起的。
- **反馈循环**：有缺陷漏过去时，系统记下原因，把它变成一份文档、一个 skill、一条 lint 规则或一个工具，让缺陷率随时间下降。
- 人从执行转向意图、判断、治理和系统设计。

### 4. 建工厂的前提
- 工具访问、隔离的控制面、代理就绪度。
- 代理就绪度引用 Cursor 的 Eric Zakariasson 在 AIE Europe 2026 的演讲，拆成三条：
  - **能跑起来**：代理能不能在没有人参与的情况下启动你的开发环境？能的话就可以在独立虚拟机上横向扩展；
  - **能拿到**：代理能不能接触到任务相关的外部上下文和工具？
  - **能验证**：它能不能验证自己的改动？演讲者认为大家应该多花时间构建可验证的系统。

### 5. 软件工厂的结构
- 课件引用 Zach Lloyd 的一张图（图未转载，见课件），从左往右读：
  - 任务从 Slack、Linear、GitHub issue、定时任务或告警进来；
  - 编排器依次跑分诊、写规格、实现、审查、验证；
  - 然后交付（PR、合并、部署）并监控。
- 一切由写在代码里的工厂定义管理：skills、规则 / AGENTS.md、自动化配置。每个代理在自己的隔离沙箱里运行；验证包括测试 / CI、AI 评审员和计算机操作（computer-use）检查。
- 人守三道关：批准规格、按风险分级的审查、产品检查。
- 两条回路：监控把新问题送回分诊；遥测（每个 PR 的成本、周期、人工介入次数）让观察代理给工厂定义提 PR，由人合并。

### 6. 工厂里的一次完整流程（引自 Zach Lloyd）
1. 分诊代理尝试理解并复现问题：能自动化的交给实现代理；范围或含义不清的交给规格代理；太模糊的找人补充后重跑，或者先搁置；
2. （需要时）规格代理写规格，人审过后交给实现代理；
3. 实现代理写代码；
4. 审查代理审代码；
5. 验证代理用计算机操作等方式验证；
6. 人审查代码和验证结果，必要时退回第 2–5 步；
7. CI / CD；
8. 发布；
9. 监控代理运行，发现问题就建 issue，回到起点。

### 7. 适合放进工厂的任务
PR 审查、CI 失败、合并冲突、生产事故的初步调查、安全漏洞。

### 8. 人做什么
- 从工人变成管理者：同步做计划，异步做执行；
- 审查按风险分配：安全、数据和支付由人负责；
- 代理跑偏是改进工厂的信号；
- 发布出去的东西仍由人负责。

### 9. 评审员给每次运行打分
- 用大模型评审员对照规格给整次运行打分，而不是凭感觉。课件提到 Zach Lloyd 演示过一个专门抓「代理写了多余测试」的评分器。
- Spotify Honk 的评审员对照原始提示词检查 diff，否决约四分之一的会话，被否决后约一半能自己纠正，最常见原因是做了提示词以外的事。

### 10. 用自己的历史做基准
- 私有基准比公开基准更可靠：重放自己过去的任务，比较不同模型和框架在成本和质量上的取舍。

### 11. 工厂的指标
- 每个 PR 的成本和周期；
- 每个 PR 的人工介入次数；
- 合并的 PR 里经过工厂的比例；
- 不看代码行数，也不看 token 数。
- 课件提醒：Zach Lloyd 报告的每 PR 成本在下降，但不同来源给出的具体数字不一，只当趋势看。

### 12. 两种搭法
- **拼装式（Frankenstein）**：把现有的工作流（Claude 自动化、Devin 等）拼起来；
- **基础设施即代码**：完整的工厂定义像 Terraform 一样写成代码（如 Warp），是仓库里有版本的文件，可以 diff、审查、回滚。

### 13. 爬、走、跑
- 爬：先把自动化用在杂活上（分诊、审查、修 Sentry 报错、CI 自愈），选测试完善、结构标准的仓库；
- 走：在一个简单的产品面上跑通一个端到端的工厂；
- 跑：再上复杂的仓库。
- 去人已经在用的地方（Slack、Linear、GitHub），不要另开一个门户；鼓励使用，不强制；按风险分级决定哪些改动自动批准、哪些交给人。

## 本周阅读要点

### Warp 工厂示例：从 issue 到 PR
- 一个完整的工程工厂：接收 Slack、Linear、GitHub 的请求，经过分诊、（需要时）写规格、实现，再由另一个代理审查，最后把 PR 交给人。
- 五个默认代理 FOREMAN、TRIAGE、SPEC、IMPLEMENT、REVIEW，外加一个处理其他工作的自定义代理；审查代理用的模型和实现代理不同，减少共同的盲点。
- 不同阶段用不同规格的运行环境：读代码、写文字的阶段用 4 核 8 GB 的 Linux；编译和跑测试的实现阶段用 8 核 16 GB；移动端构建用 macOS。
- GitHub 入口用「被 @ 或被指派」加「带路由标签」两个条件同时满足才触发，示例特别提醒放宽过滤条件要小心。
- 还配了评分器：一个给实现运行打分并开启自我改进，一个给审查运行打分。

### The Software Factory（Ona 的公开实验）
- 目标：完全不写人工代码，用代理做出一个真实产品（类 Notion 的笔记应用 Memo），十天直播全过程。
- 第十天的数字：合并 375 个 PR、5 万多行代码、16 个自动化、1,067 个测试、自主率 87%、PR 到合并的中位时间 4.9 分钟。
- 主要体会：规格质量决定产出质量；运维那一侧需要的自动化比构建那一侧更多。
- 公司 COO 压测后报了 12 个 bug，工厂也在修 bug，但修的不是同一批：Sentry 能抓住运行时错误，视觉和交互问题还得靠人指出来。

### OpenInspect
- 一个开源、可自托管的后台编程代理框架，思路来自 Ramp 的 Inspect（第 8 周阅读）。
- 控制面用 Cloudflare Workers 和 Durable Objects 管理会话和流式传输，数据面用 Modal 沙箱运行代理，网页端是 Next.js 加 GitHub 登录。
- 卖点是让产品经理、设计师也能直接把想法变成 PR，会话可以多人协作。

### WarpBench：评估编程代理
- Warp 让 foreman 代理从过去的代理运行里挑出 30 个有代表性的任务（按 S、M、L、XL 分级），在原始环境里重放，用评审员按成本、质量等维度打分。
- 一次完整跑下来用了 3 小时 46 分钟、2,130.57 美元，所以文章建议只在新模型发布或配置大改时跑。
- 根据结果更换默认实现模型后，Warp 内部每个完成的 PR 成本从约 80 美元降到约 30 美元，合并率不变，任务合规分从 69% 升到 87%（文章自述数字）。
