## 整体结构（5 块）
| 模块 | 作用 |
|---|---|
| `SYSTEM_PROMPT` | 系统提示词模板，留一个 `{tool_list_str}` 占位，用来填工具说明 |
| 3 个工具函数 | `read_file_tool` / `list_files_tool` / `edit_file_tool` |
| `TOOL_REGISTRY` + 工具描述生成 | 用函数的 docstring 和签名自动生成给模型看的工具说明 |
| `extract_tool_invocations` | 从模型回复里解析出 `tool: 名字({JSON})` 这样的行 |
| `run_coding_agent_loop` | 主循环：读用户输入 → 调模型 → 有工具调用就执行、回填结果再调模型 → 没有就输出 |

运行环境：Python 3.12+，依赖 `openai`、`python-dotenv`，`.env` 里写 `OPENAI_API_KEY`；代码用 OpenAI 的 Responses API，模型名为 `gpt-5.6-terra`。

## 1. 系统提示词
大意：告诉模型它是编程助手；列出可用工具（用占位自动填入）；要调用工具时只输出一行 `tool: 工具名({JSON参数})`，JSON 写成一行、用双引号；收到 `tool_result(...)` 后继续任务；不需要工具就正常回答。

代码没有用 API 原生的 function calling，而是靠提示词约定文本格式，再自己解析。

> [!NOTE]
> **补充**
> 这样写最能看清“工具调用”的本质：它就是一种**文本协议**。

## 2. 三个工具
- `resolve_abs_path`：把相对路径换成基于当前目录的绝对路径，支持 `~`。
- `read_file_tool(filename)`：返回 `{"file_path", "content"}`。
- `list_files_tool(path)`：列出目录，每项标明 `file` 或 `dir`。
- `edit_file_tool(path, old_str, new_str)`：
  - `old_str` 为空 → 用 `new_str` 新建或覆盖文件；
  - 找不到 `old_str` → 返回 `old_str not found`，把错误交给模型，而不是让程序崩掉；
  - 找到了 → 只替换第一处。

> [!NOTE]
> **补充**
> `edit_file_tool` 的“精确字符串替换”，和 Claude Code 里 `Edit` 工具的做法是同一个思路。

## 3. 工具说明怎么自动生成
从 `TOOL_REGISTRY` 取出函数，把函数名、`__doc__`（docstring）和 `inspect.signature`（签名）拼成一段文字，填进系统提示词。简化示意：
```python
def describe(name, fn):
    return f"Name: {name}\nDescription: {fn.__doc__}\nSignature: {inspect.signature(fn)}"
```
这正对应 9/24 课件的一句：工具的描述、名字和完整签名都是提示词的一部分。

## 4. 解析工具调用
逐行找以 `tool:` 开头的行，按 `(` 切出工具名，再用 `json.JSONDecoder().raw_decode` 解析后面的 JSON；格式不对的行直接跳过。

## 5. 主循环（agent loop）
```
conversation = [developer 角色：系统提示词]
外层循环：读用户输入 → 追加 user 消息
  内层循环：
    回复 = 调 LLM(conversation)
    没有工具调用 → 打印回复，追加 assistant 消息，回到外层等输入
    有工具调用 → 追加 assistant 消息；逐个执行工具，
               把结果以 user 角色写成 "tool_result({json})" 追加 → 再调 LLM
```

> [!NOTE]
> **补充**
> - 对话列表只会追加，这就是上下文窗口不断变长、后面要学压缩（compaction）的原因。
> - 工具结果用 `user` 角色回填，和 9/24 课上抓包看到的 Claude Code 一样。
