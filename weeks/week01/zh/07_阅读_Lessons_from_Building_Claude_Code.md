## 核心问题：怎么设计代理的“行动空间（action space）”
- 工具可以有很多种形态：bash、skills、代码执行（programmatic tool calling）……是只给一个万能工具，还是给 50 个专用工具？
- 作者的比喻：给你一道难的数学题，你要什么工具，取决于你自己会什么。纸笔是最低配置，计算器更好，电脑最强，但前提是你会写代码。
- 结论：**工具要贴合模型自己的能力**。怎么知道它的能力？多观察、读它的输出、做实验。这就是 “See like an agent（像代理一样看问题）”。

## 案例 1：AskUserQuestion 工具（提升“提问/引导澄清 elicitation”能力）
- 尝试 1：给 ExitPlanTool 加一个“问题数组”参数 → 模型被搞糊涂了（又要交计划又要提问，答案和计划冲突怎么办？）
- 尝试 2：规定一种特殊的 Markdown 提问格式，再解析成 UI → 格式不稳定（模型会多写句子、漏掉选项、换格式）
- 尝试 3：做成专门的工具，在计划模式下特别提示它用；弹出窗口，等用户回答完才继续循环 → 结构化输出，保证给出多个选项，还能在 Agent SDK 和 skills 里复用。**而且模型“喜欢”调用它。**
- 教训：设计得再好的工具，模型不会用也没用。

## 案例 2：从 Todo 到 Tasks（工具要跟着模型能力一起变）
- 早期：给 TodoWrite 工具让模型别跑偏，还每 5 轮插一次系统提醒（system reminder）。
- 模型变强以后，提醒反而成了**束缚**：模型以为必须死守清单，不敢改。
- 子代理协作需要共享任务 → 用 Task 工具替换了 TodoWrite。Tasks 支持依赖关系、跨子代理同步，模型也能修改和删除。
- 教训：**以前需要的工具，现在可能在限制模型**，要经常重新检查。也最好只支持能力相近的少数几个模型。

## 案例 3：搜索接口，从 RAG 到 Grep
- 一开始用 RAG 向量库给 Claude 找上下文：快，但要建索引、要配置，在各种环境里容易出问题，而且是“喂”上下文，不是让模型自己找。
- 改成给 Grep 工具，让模型**自己搜、自己构建上下文**。
- Agent Skills 把**渐进式披露（progressive disclosure）**正式化了：skill 文件可以引用别的文件，模型按需递归读取。
- 一年里，Claude 从“不太会自己找上下文”进步到“能跨好几层文件做嵌套搜索”。

## 案例 4：Claude Code Guide 子代理（不加工具，也能扩展能力）
- Claude Code 现在大约 20 个工具（原文的数字），**加新工具门槛很高**，因为每多一个工具，模型就多一个要考虑的选项。
- 问题：模型不了解 Claude Code 自己怎么用（比如怎么加 MCP）。
- 写进系统提示词？用户很少问这个，会造成上下文腐烂（context rot）。给文档链接？模型会把一大堆搜索结果塞进上下文。
- 最终做法：建一个专门的 Guide 子代理，专门负责查文档，只把答案带回来。

## 结论
没有死规则，工具设计**既是艺术也是科学**，取决于模型、目标和环境。多实验、多读输出、像代理一样看问题。
