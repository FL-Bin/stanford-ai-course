## 二、从“200 行代理”到现代框架
- 周二是概念验证：200 行代码能做到什么。今天要把编程代理和它的框架带到当下，拆解一个最先进的编程代理。
- 除了智能层（模型本身，私有、看不到），框架里的一切都能看到。
- 演示对象：Claude Code + Opus 5.5（发布才两天）。讲师顺带提到 OpenAI 同一天也发了新模型。
- 核心循环：用户通过框架的界面交互 → 框架调用大模型 → 和一组工具来回交互；工具让模型“落地”，能搜索网页、操作文件系统。今天讲的是循环之外的所有部件，统称框架（harness）。
- 框架设计可能是编程代理乃至所有代理里最难也最重要的问题，这些原则同样适用于销售、法律、客服等领域。

> [!NOTE]
> "We'll be able to see everything except the intelligence layer, which is the model."
> 除了智能层，也就是模型本身，其余的我们都能看到。
> —— 9/24 文字稿

## 三、演示方法：抓包看请求
- 用代理工具（proxy）拦截 Claude Code 的请求和响应，类似 Wireshark 或浏览器调试台。第一次作业就是自己做这件事（周日截止）。
- 演示项目：讲师做的命令行待办工具（todo CLI）。
- 请求结构：`model` + `messages`（user / assistant / system 三种角色）+ `tools` + `system`。user 消息通常是讲师输入的内容，也可能是工具调用结果；system 消息是框架在背后注入的；assistant 消息是 Claude 在做事，比如发起工具调用。

## 四、工具列表（Tool List）
- `tools` 是一个列表，每项包括名字、描述、参数 schema（相当于函数签名）。例如 `Agent` 工具用来启动子代理。
- 约 40 个原生工具：文件、Bash、Monitor、WebSearch、LSP、代理类、计划/隔离、定时、Artifact、MCP 资源、交互等。
- 除原生工具外还有 MCP 工具（把外部工具和资源接入框架的一种方式），名字带 `mcp__` 前缀。
- 所有工具定义每次请求都会进入上下文，MCP 装太多会把上下文撑满、效果变差。
- MCP 和 Skills 的区别：MCP 工具是最小原语，像一次 API 调用；Skill 把工具、脚本和串联它们的提示词组合成多步流程，并采用渐进式披露（progressive disclosure）：先只放少量元数据，用到时再加载全文。
- 历史观察：Claude Code 去年 12 月前后走红，原因之一是**极简框架**，长期只有一组受限但几乎什么都能做的工具；40 个在这个意义上也不算多。早期一些 MCP 服务器有上百个工具，非常臃肿。行业趋势是降低复杂度：从 3–5 个能干很多事的工具起步，像“瑞士军刀”一样的 SQL 和 Bash 就是例子。
- 问答：为什么代理之间用自然语言而不是向量通信？因为训练数据和人工标注都是文本，人也看不懂向量。

## 五、系统提示词（System Prompt）
- 一段定义框架行为、护栏和环境信息的文本，由框架静态注入；你控制不了它，但每次请求都带着它。
- 第一块是 “You are Claude Code, Anthropic's official CLI for Claude.”（你是 Claude Code，Anthropic 官方的 Claude 命令行工具）；第二块是主要指令：交互式软件工程代理、安全相关的注意事项、框架说明、会话说明、一大块关于记忆（memory）的内容、环境信息、上下文管理。
- 讲师提到这一版只有 50–80 行左右，以前有 200–250 行（还要教模型怎么用 Git 之类），推测这些知识已经训练进模型。第一次请求前，上下文可能已被占用几万 token。
- 泄露问题：抓包本来就不难，Codex 的框架更是直接放在 GitHub 上，所以“看得到框架”算不上大的攻击面。
- 记忆为什么不用 RAG / GraphRAG？基准测试显示，平铺的文本文件（flat files）往往就够用；讲师所在公司做销售代理，也是用平铺文件做记忆。

## 六、CLAUDE.md / AGENTS.md
- 它是系统提示词的“用户可控版”：系统提示词由框架设定、静态注入；CLAUDE.md 也会被注入，但内容由我们控制。
- AGENTS.md 是通用约定，CLAUDE.md 是 Claude 专用，作用相同，可用软链接把两者连起来。
- 框架把它注入在第一条 user 消息前面，并注明这些指令覆盖默认行为。讲师还指出，第一条 user 块里很多内容（比如 system reminder）不是他输入的，而是框架在背后加的。
- 经验：写清运行、测试、启动服务的命令即可，不要写太多，以免过度约束模型，一般也不放大段代码。

## 七、计划模式（Plan Mode）
- 大约 9 个多月前，大多数编程框架都加入了计划模式：用来写规格，和用户来回澄清需求和架构。
- 有进入工具和退出工具；进入时框架注入一大段计划提示词，流程分阶段：理解需求（可派 Explore 子代理）→ 设计 → 审查 → 最终计划，然后退出。这一思路适用于几乎所有现代编程框架，包括 Codex。
- 产出物是 plan 文件。演示需求是给 todo 应用加周期任务（如“每周浇花”）。

## 八、Skills
- 本质是写下来的流程：多个工具调用 + 脚本 + 串起它们的提示词；可由代理主动触发，也可由用户明确调用。
- 演示了讲师写的 “check code quality” skill：框架先注入一条命令消息，提示模型该检查代码质量了，再找到 SKILL.md 文件，把全文读进上下文。

## 九、子代理（Subagents）
- 主代理作为协调者（orchestrator），派出带全新上下文的 worker，可以并行，结束后把结果交回；探索过程不会污染主上下文。

## 十、Hooks 与 Compaction
- Hooks 只简单提了一下。
- Compaction：上下文接近上限时自动触发，或手动触发；有专门的汇总提示词；用摘要替换原上下文（例如 50 万 token 压到 15 万）。

## 十一、总结
- 趋势是简单：工具更少更强，更多依赖模型能力而不是框架。业界在“投入模型”和“投入框架”之间来回摆动，现在偏向“框架越简洁越好”。
- “dumb zone（变笨区）”：讲师强调这不是正式术语，只是玩笑说法，指上下文太长后模型效果变差。
- 提示词趋向更短，也更容易调整。
