## 二、从“200 行代理”到现代框架（harness）
- 周二的演示证明：150–200 行代码就能做出编程代理的骨架。
- 今天拆解最先进的编程代理：**除了模型本身（智能层，看不到），框架里的东西都能看到**。
- 演示对象：Claude Code + Opus 5.5（发布才两天）。讲师顺带提到 OpenAI 同一天也发了新模型。
- 核心观点：**框架设计可能是编程代理乃至所有代理里最难、最重要的问题**，同样适用于销售、法律、客服等领域。
- 核心循环：上下文窗口（context window）+ 模型 + 工具执行。今天讲的是循环之外的所有部件。

## 三、演示方法：抓包看请求
- 用一个代理工具（proxy）拦截 Claude Code 的请求和响应，类似 Wireshark 或浏览器调试台。**第一次作业就是自己做这个**（周日截止）。
- 演示项目：讲师 vibe coding 出来的命令行待办工具（todo CLI）。
- 请求结构：`model` + `messages`（user / assistant / system 三种角色）+ `tools` + `system`。有些消息是框架在背后偷偷注入的。

## 四、工具列表（Tool List）
- `tools` 是一个列表，每项是字典：名字、描述、参数 schema（相当于函数签名）。例如 `Agent` 工具用来启动子代理。
- 约 40 个原生工具：文件、Bash、Monitor、WebSearch、LSP（语言服务器协议）、代理类、计划/隔离、定时（cron）、Artifact、MCP 资源、交互（提问、推送通知、反馈）等。
- MCP 工具名带 `mcp__` 前缀（如 Claude Docs、Mintlify、Notion、Slack）。
- **所有工具定义每次请求都会全部塞进上下文**，所以 MCP 装太多会把上下文撑爆，效果变差。
- **MCP 和 Skills 的区别**：MCP 工具是最小原语，像一次 API 调用（输入→输出）；Skill 把工具、脚本和中间的提示词组合成多步流程，而且用**渐进式披露（progressive disclosure）**：一开始只放少量元数据，用到时才加载全文。
- 历史经验：Claude Code 在去年 12 月左右走红，原因之一是**框架极简**。早期 GitHub 的 MCP 服务器有 110 个左右的工具，非常臃肿。趋势是 3–5 个强大工具起步（Bash、SQL 这类“瑞士军刀”）。
- 问答：为什么代理之间用自然语言而不是向量通信？因为训练数据和人工标注都是文本，人也看不懂向量。

## 五、系统提示词（System Prompt）
- 请求里有个 `system` 块：第一段是 “You are Claude Code, Anthropic's official CLI for Claude.”（你是 Claude Code，Anthropic 官方的 Claude 命令行工具），第二段是主要指令。
- Opus 5.5 版只有 50–80 行左右，以前是 200–250 行（还要教模型怎么用 Git 之类）。讲师推测这些知识已经通过训练进了模型参数。
- 内容包括：身份、安全要求、框架说明、会话说明、**记忆（memory）**（按项目存放在文件系统里，有固定格式）、环境（可用模型等）、上下文管理。
- 你控制不了它，但它每次都占你的上下文。第一次请求前可能已经被用掉几万 token。
- 泄露问题：抓包本来就不难，Codex 的框架更是直接开源在 GitHub 上，所以“看得到框架”不算大的攻击面。
- 记忆检索为什么不用 RAG / GraphRAG？基准测试显示，平铺的文本文件（flat files）往往就够用。讲师自己公司的销售代理也是用平铺文件做记忆。

## 六、CLAUDE.md / AGENTS.md
- AGENTS.md 是通用标准，CLAUDE.md 是 Claude 专用的，功能一样。可以用软链接（symlink）把两者连起来。
- 它是“用户能控制的系统提示词”，框架会把它注入到第一条 user 消息前面，还会注明 “OVERRIDE any default behavior（覆盖所有默认行为）”。
- 经验：写上运行、测试、启动服务的命令就好，**不要写太多**，否则会把模型约束过度（overfitting），一般也不放大段代码。

## 七、计划模式（Plan Mode）
- 9 个多月前各家框架都加了这个模式：用来写规格，跟用户来回澄清需求和架构。
- 有进入工具和退出工具；进入时框架会注入一大段计划提示词，流程分阶段：① 理解需求（可以派 Explore 子代理）→ ② 设计 → 审查 → 最终计划，最后退出。
- 产出物是 **plan 文件**。演示的需求是给 todo 应用加周期任务（比如“每周浇花”）。

## 八、Skills
- 本质是写下来的流程：多个工具调用 + 脚本 + 串起它们的提示词。可以由代理主动触发，也可以由用户明确调用。
- 演示了讲师写的 “check code quality” skill：一个 SKILL.md，描述什么是好代码、什么是坏代码。调用时框架先注入一条命令消息，再把 SKILL.md 全文读进上下文。

## 九、子代理（Subagents）
- 主代理是协调者（orchestrator），派出带全新上下文的 worker，可以并行，结束后把结果交回。**好处是探索过程不污染主上下文。**

## 十、Hooks 与 Compaction
- Hooks 只简单提了一下。
- Compaction：上下文接近上限时自动触发，或者手动触发；有专门的汇总提示词；汇总替换原上下文（比如 50 万 token 压到 15 万）。

## 十一、总结
- 趋势是**简单**：工具更少更强，更依赖模型能力而不是框架。业界在“投资模型”和“投资框架”之间来回摇摆，现在偏向“框架越简洁越好”。
- “dumb zone（变笨区）”：讲师强调这不是正式术语，只是开玩笑的叫法，指上下文太长后模型效果变差。
- 提示词趋向更短，也更容易调整。
