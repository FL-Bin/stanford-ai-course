## 第 3 讲｜9/29：复杂代码库里的进阶提示词与上下文工程
### 目标
- 从“随手写提示词（ad-hoc prompting）”升级到**稳定、可靠的同步 AI 开发流程**。
- 用 AI 快速上手陌生代码库，并系统地完成复杂任务。

### 为什么不能只靠 vibe coding
- **Vibe coding（凭感觉编程）**：不怎么思考、一路 Tab 接受 AI 代码。做小玩具很爽，但在几百上千个文件、几百万行代码的生产代码库里不够用。
- 规模一大，就撞上**上下文窗口（context window）的限制**。窗口再大（有的到百万 token），也不是每个 token 都一样“聪明”。
- 讲师的观点：写生产级 AI 代码必须**有方法**，你脑子里要有一个**能运转的心智模型（mental model）**——知道方案大概会怎么搭。
- 现在的“坏代码”有两种：架构决策错误，以及模型幻觉导致的功能错误。

### RePPIT 框架（讲师提出的流程）
| 字母 | 阶段 | 做什么（我们的理解） | 产出物 |
|---|---|---|---|
| R | Research 调研 | 让代理把代码库“蒸馏”成一份结构化调研文档：有哪些模块、怎么组织、关键代码在哪；**不要把原始代码全塞进上下文** | 调研文档 |
| P | Propose 提方案 | 基于调研文档给出 2 个左右方案并对比取舍（讲师经验：超过 2 个收益递减） | 方案对比 |
| P | Plan 计划 | 把选中的方案写成详细计划：要改哪些文件（像预览 diff）、测试怎么做、可观测性、**明确写出不做什么（out of scope）** | 计划文档 |
| I | Implement 实现 | 让代理按计划实现，这一步的提示词反而最简单 | 代码 |
| T | Test 测试 | 单元测试、集成测试、冒烟测试；还可以让代理用一个审查 skill 检查架构、风格、一致性 | 测试与审查报告 |

课上演示：给一个类似 Mint 的记账应用加“按类别显示消费趋势线”功能，按 RePPIT 一步步走；讲师选了只改前端的轻量方案。

### 实用经验（转述）
- **上下文预算**：上下文窗口里只有前 ½–¾ 是“聪明 token”，再往后就是讲师说的 “dumb zone”。系统提示词、AGENTS.md/CLAUDE.md 已经先占了一部分。
- **认真审 spec**；功能很大时拆成任务清单；每完成一项，把代理做了什么写成文档，作为下一项的上下文。
- 已有文档：维护得好就复用；过时的文档**宁可不要**，免得误导代理。
- **模型分工**：调研、方案、计划这些“想”的阶段用最强的模型；实现和测试可以用轻一点的模型。
- 没选中的方案还留在上下文里会浪费 token——适时清空或压缩上下文。课上引用的一篇压缩研究认为，大约在 25 万–45 万 token 之间压缩比较合适（因模型而异）。
- RePPIT 不是死规定，讲师鼓励按自己的领域改造它。

### 任务委派的四个层级（Task delegation taxonomy）
1. 直接提示（simple prompting）——小改动
2. 先做计划再实现（make a plan）
3. 先调研再计划（research then plan）
4. 多轮“调研→计划”（(research then plan) × N）——大功能

### 其他规格驱动（spec-driven）框架
- **Superpowers**：一套有主见的端到端流程，基于 TDD，提供写 spec/计划、实现、测试的一组 skills，内置并行。
- **OpenSpec**：更轻量的 spec 与计划流程，特点是把“变更”与“唯一事实来源的 spec”分开追踪，完成后再合并。
- **spec 放哪里**：Linear 之类的工具，或者放在仓库里用 Git 管理；设计取舍可以放在 `.notes/` 目录。

## 第 4 讲｜10/1：MCP、工具调用及更多（MCP, Tool-calling, and Beyond）
### 为什么需要 MCP
- 大模型的知识是训练时的**静态快照**；要做真正自主的系统，就得有可靠的方式把**动态数据**送进来。

### MCP 是什么
- **Model Context Protocol（模型上下文协议）**：一个开放协议，用通用的方式把上下文/工具提供给模型。说白了：**给大模型暴露工具的标准格式**。
- 好处：把 M 个模型/代理 × N 个服务的 **M×N 个连接器**变成 **M+N**；认证、错误处理、限流不用每家重做；用 JSON-RPC 统一输出格式。

### 术语和流程
| 术语 | 含义 |
|---|---|
| Host 宿主 | Cursor、Claude Desktop 等应用 |
| MCP Client 客户端 | 嵌在宿主里的库，每个服务器一个有状态会话 |
| MCP Server 服务器 | 包在某个工具/服务前面的轻量封装 |
| Tool 工具 | 可调用的函数（数据源、API 等） |

流程：客户端调 `tools/list` 问“你能做什么” → 服务器返回每个工具的名字、说明和 JSON schema → 宿主把这些塞进模型上下文 → 用户提问后模型输出结构化的工具调用 → 服务器执行并返回，对话继续。传输层支持 **stdio** 和 **streamable HTTP**。

### 怎么设计好的 MCP 服务器
**做法一：别把它当 REST API 的简单包装。** 一个端点对应一个工具会导致工具太多、上下文太大、代理把时间花在编排上（讲师说 2024–2025 年初大家这么试过，效果很差）。
- **面向结果，而不是面向操作**：例如做一个“按邮箱付款”的工具，而不是让模型先查用户、再查账户、再付款，连续三次调用都要对。
- **参数要明确**：别用嵌套的大字典；用类型注解、Pydantic 描述清楚。
- **说明就是提示词**：docstring、错误信息都会被模型读到。
- **命名便于发现**：工具名加服务前缀。
- 工具一多就合并：比如把“搜会议 / 搜文字稿 / 搜 Slack”合并成一个带资源参数的 `search_resource`。

**做法二：MCP 服务器数量爆炸以后，只暴露两个工具：`search` 和 `execute`。** 代理先搜索相关工具和定义，再生成一段确定性的代码去执行（在沙箱/VM 里跑，不是模型自己跑）。按需加载工具、在数据进入模型前先过滤，课件给出的数字是 token 减少 90% 以上。

**进阶：MCP 门户（portal）**（Cloudflare 的企业做法）：员工只连一个门户，就能看到自己有权使用的所有内部和第三方 MCP 服务器，并统一做日志、策略和防数据泄露。后面课程还会细讲。

### Agent Skills 预告与三者对比
- Skill：按需动态加载的能力标准，面向特定领域，把代码和提示词结合起来（写文档、做 PPT、数据分析……）。下一周专门讲。

| | API | MCP | Skills |
|---|---|---|---|
| 是什么 | 给开发者调用的 HTTP/REST/GraphQL 接口 | 让代理用标准方式调用的工具定义 | 教代理完成一类任务的可复用流程，常编排多个工具 |
| 谁来用 | 你或 SDK | 模型/代理运行时 | 代理或代理框架 |
| 定位 | 认证、重试、分页等都由你处理 | 访问外部资源和服务的主要方式 | 工作流抽象：“做 X 的标准做法” |
